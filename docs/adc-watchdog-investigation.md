# PHY6252 ADC watchdog reset — расследование и диагностическая ветка

Дата: 2026-07-14  
Ветка: `fix/phy6252-adc-watchdog`

## Вывод

Наиболее вероятная причина reset-loop — не вычисления в callback и не сам факт
одновременной работы BLE и ADC. Проблемный участок находится в драйвере ADC из
PHY62XX SDK 3.1.1:

1. одноразовое преобразование завершается внутри `ADCC_IRQn`;
2. IRQ вызывает `hal_adc_stop()`;
3. `hal_adc_stop()` выполняет неограниченный цикл ожидания
   `while (AP_ADCC->intr_status != 0)`;
4. тайм-аут в SDK выключен (`ADC_USE_TIMEOUT=0`);
5. если status не снимается или успевает выставиться повторно, процессор остаётся
   в IRQ дольше 2 секунд;
6. OSAL idle не получает управление и не кормит watchdog — происходит reset.

Это согласуется с поведением на плате: после включения периодического ADC плата
уходит в watchdog reset-loop, а перенос float-обработки из ISR в OSAL task ничего
не меняет.

## Почему это не просто гипотеза про clock coexistence

В открытой PHY62XX SDK 3.1.2 компания Phyplus изменила ровно этот путь:

- убрала неограниченный цикл очистки `intr_status`;
- для one-shot использует отдельный `hal_poilling_adc_stop()`;
- сбрасывает модуль `MOD_ADCC`;
- очищает pending IRQ;
- больше не выключает ADC clock bit 13 при каждом stop;
- исправила разбор sample-регистров: в 3.1.1 соседние элементы массива
  перезаписывались, в 3.1.2 из каждого 32-битного регистра извлекаются два
  независимых 12-битных отсчёта.

Release notes 3.1.2 отдельно отмечают переработку ADC driver/demo.

## Что изменено в ветке

### `Firmware/phy6252/dpls_adc_phy6252.c`

Минимальный драйвер, совместимый с текущим `adc.h` SDK 3.1.1:

- нет polling-loop без тайм-аута;
- one-shot корректно завершается из IRQ;
- ADCC reset + clock gate + pending IRQ clear как в SDK 3.1.2;
- общий CLKHF/DLL не дёргается вниз на каждом stop;
- исправлена распаковка двух 12-битных samples из регистра;
- IRQ реагирует на полученные ожидаемые биты, а не требует точного равенства
  всего `intr_status`;
- поддерживаются стандартные single-ended ADC channels; для продукта нужны P20
  и P23.

Старый `components/driver/adc/adc.c` исключён только из target-сборки
Test-DPLS. Файл SDK не изменялся.

### `Firmware/phy6252/dpls_adc_soak.c`

Отдельная OSAL-задача запускает one-shot ADC раз в секунду, пока штатное BLE-
приложение продолжает advertising/connection/GATT работу.

По умолчанию активен только P20 — это первый контролируемый эксперимент.
Каждые 10 успешных измерений UART печатает:

```text
[ADC SOAK] ok n=10 p20=... mV starts=10 timeout=0 err=0
```

Если ADC не завершился за 500 мс:

```text
[ADC SOAK] TIMEOUT ...
```

Если процессор снова зависнет внутри IRQ, timeout-задача не успеет выполниться,
но следующий boot покажет `[REST CAUSE]` — это отличает IRQ lockup от обычной
ошибки запуска/события.

## Матрица испытаний

Каждый этап выполнять последовательно. Переходить дальше только при нуле reset,
timeout и start error.

### A. P20, advertising, без телефона

1. Собрать и прошить ветку.
2. Не подключать телефон.
3. Снять UART минимум 15 минут.
4. Критерий: не менее 800 `completed`, `timeout=0`, нет повторных boot/reset.

### B. P20, BLE connected idle

1. Подключить Android и пройти авторизацию.
2. Оставить соединение на 15 минут.
3. Критерий тот же; приложение не теряет связь.

### C. P20, активный BLE

В течение 15 минут циклически:

- запрашивать состояние;
- переключать безопасные тестовые режимы на макете;
- выгружать журнал;
- выполнять reconnect.

Критерий: ноль reset/timeout/error, GATT-ответы не теряются.

### D. P20 + P23

В `dpls_adc_soak.c` установить:

```c
#define DPLS_ADC_SOAK_INCLUDE_VCAP 1
```

Повторить A–C, затем оставить connected soak минимум на 2 часа.

### E. Интеграция в product path

Только после успешного D:

1. убрать диагностическую OSAL-задачу;
2. включить `DPLS_ADC_SAMPLING` в `dpls_phy6252_app.c`;
3. использовать тот же исправленный драйвер;
4. повторить двухчасовой soak;
5. выполнить калибровку P20/P23 и проверить потребление.

## Дополнительные находки

### P20 используется ещё и как вход в RF direct test

В текущем `main.c` есть:

```c
if (hal_gpio_read(P20) == 1)
    rf_phy_direct_test();
```

На PB-03F P20 одновременно является ADC9 линии. При подключённом делителе высокий
уровень на старте потенциально может отправить серийное устройство в DTM вместо
обычной прошивки. Это не объясняет периодический reset-loop, но до подключения
силовой платы этот boot strap нужно убрать или перенести на отдельный сервисный
пин.

### P23 имеет совмещённую функцию microphone-bias reference

Драйвер перед измерением отключает micbias и переводит P23 в analog input. После
стабилизации необходимо проверить, что схема PB-03F и внешняя обвязка действительно
позволяют использовать P23 как канал VCAP без побочных токов.

## Что пока нельзя считать доказанным

- Исправление ещё не проверено на живой PB-03F.
- Не измерено влияние сохранённого ADC clock bit 13 на среднее потребление.
- Не проверена работа сразу двух каналов.
- Не выполнена калибровка и проверка диапазона 0…30 В.

До успешного hardware soak ветку нельзя сливать в `main` и нельзя включать ADC в
серийной конфигурации.
