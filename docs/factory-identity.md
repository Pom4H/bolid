# Серийная идентификация Test-DPLS

Этот документ описывает схему идентификации устройства для серийного производства Test-DPLS на PHY6252/PB-03F.

Цель: серийный номер прибора, BLE identity и долговременные BLE-ключи создаются один раз при выпуске платы и не зависят от версии прошивки, пользовательских настроек, журнала и factory reset.

## 1. Что считается идентичностью прибора

Идентичность разделена на независимые сущности:

| Сущность | Назначение | Может меняться при обычной эксплуатации |
|---|---|---|
| `serial_number` | главный ID прибора в приложении, протоколе и производственной БД | нет |
| BLE address | транспортный адрес Bluetooth LE | нет |
| IRK / CSRK | долговременные BLE identity/signing keys | нет |
| пользовательское имя | удобное имя, задаваемое приложением | да |
| пароль/верификатор | прикладная аутентификация Test-DPLS | да |
| bonds | состояние сопряжения конкретных телефонов | да |
| журнал | эксплуатационные события | да |

`device_id` протокола остаётся 32-битным ради совместимости с существующим мобильным приложением, но теперь его источником является `serial_number`, а не первые четыре байта MAC.

Имя в эфире остаётся `Test-DPLS-XXXX`, где `XXXX` — младшие 16 бит серийного номера в HEX. Полный 32-битный номер читается после подключения через `DEVICE_INFO_REPORT`.

## 2. Factory sector

Под factory identity выделен последний сектор 4 КиБ в используемом flash-окне:

```text
0x11020000 ─┐
            │ application XIP
            │ 0x1F000 bytes
0x1103BFFF ─┘

0x1103C000 ─┐
            │ SNV filesystem, 3 × 4 KiB
0x1103EFFF ─┘

0x1103F000 ─┐
            │ FACTORY IDENTITY, 4 KiB
0x1103FFFF ─┘
```

Linker-файлы `scatter_load.sct` и `phy6252.ld` заканчивают XIP на `0x1103EFFF`, поэтому обычный firmware image никогда не содержит данных factory-сектора.

Firmware только **читает** запись из `0x1103F000`. API записи/стирания factory identity в рабочей прошивке нет.

Важно: это логически неизменяемая область, а не OTP/eFuse. Полное chip erase физически стирает её. Поэтому `tools/flash_firmware.sh --erase` заблокирован без явного `DPLS_ALLOW_FACTORY_ERASE=1`.

## 3. Формат factory record v1

В начале сектора хранится 64-байтная запись. Остаток сектора свободен для будущих версий.

| Offset | Размер | Поле |
|---:|---:|---|
| `0` | 4 | magic `DID1` |
| `4` | 2 | версия формата = `1` |
| `6` | 2 | размер записи = `64` |
| `8` | 4 | `serial_number`, LE32 |
| `12` | 2 | hardware revision |
| `14` | 2 | flags |
| `16` | 6 | BLE static address или `FF..FF` |
| `22` | 1 | BLE address source/type |
| `23` | 1 | reserved |
| `24` | 16 | IRK |
| `40` | 16 | CSRK |
| `56` | 6 | reserved |
| `62` | 2 | CRC16-CCITT-FALSE по байтам `0..61` |

Flags v1:

```text
bit 0  BLE static-random address записан в record
bit 1  IRK присутствует
bit 2  CSRK присутствует
```

Запись считается валидной только если совпали magic, версия, размер, CRC и проверки обязательных полей.

## 4. BLE address

Приоритет адреса в серийном приборе:

```text
factory record содержит static-random BLE address
        ↓ да
использовать его как ADDRTYPE_STATIC

        ↓ нет
валидный заводской MAC PHY6252
        ↓ да
использовать его как ADDRTYPE_PUBLIC

        ↓ нет
ошибка идентичности / требуется provisioning static address
```

Для обычных PB-03F предпочтительный вариант — заводской PHY6252 MAC. Он уже уникален на уровне чипа, поэтому дублировать его в factory record не требуется.

Если конкретная партия чипов не имеет пригодного заводского MAC, при provisioning генерируется BLE **static random** address. Его два старших бита должны быть `11`; этот адрес записывается в factory record и больше не меняется.

Firmware больше не генерирует случайный public-looking MAC при загрузке.

### Совместимость со старыми прототипами

Если factory record отсутствует, текущая прошивка оставляет временный migration path:

1. заводской PHY6252 MAC;
2. старый сохранённый SNV record `0x82`, если он существует и выглядит как public address.

В этом режиме `device_id` временно выводится из MAC, как в предыдущей версии. Это позволяет не вывести из строя уже прошитые PB-03F во время разработки.

**Серийный прибор считается готовым только при наличии валидного factory record.** Метод `dpls_ble_identity_is_provisioned()` позволяет отличить серийную идентичность от migration mode.

## 5. IRK и CSRK

Для серийного изделия `IRK` и `CSRK` генерируются на производстве криптографическим RNG и записываются в factory record.

При наличии factory keys firmware всегда использует их. Очистка пользовательских BLE bonds/SNV не меняет эти ключи: после reboot они снова загружаются из factory sector.

Для непровиженного прототипа сохранён старый режим: ключи создаются RNG PHY6252 и сохраняются в SNV.

## 6. Подготовка factory HEX

Для одного прибора:

```sh
python3 tools/make_factory_identity.py \
  --serial 12874 \
  --hw-revision 2 \
  --output tmp/factory-00012874.hex \
  --metadata tmp/factory-00012874.json
```

По умолчанию:

- BLE использует заводской public MAC PHY6252;
- IRK и CSRK генерируются случайно один раз;
- в JSON не записываются секретные ключи;
- HEX содержит только адреса factory-сектора `0x1103F000`.

Если заводского MAC нет:

```sh
python3 tools/make_factory_identity.py \
  --serial 12874 \
  --generate-static-address \
  --output tmp/factory-00012874.hex \
  --metadata tmp/factory-00012874.json
```

Можно передать заранее выделенный static random address:

```sh
python3 tools/make_factory_identity.py \
  --serial 12874 \
  --static-address C2:34:56:78:9A:BC \
  --output tmp/factory-00012874.hex
```

`--no-factory-keys` существует только для лабораторных экспериментов и не должен применяться в серии.

## 7. Прошивка на производстве

Рекомендуемый порядок для каждой платы:

1. присвоить следующий уникальный `serial_number` из производственной БД;
2. сформировать factory HEX;
3. прошить application firmware;
4. прошить factory HEX **без полного erase**;
5. перезапустить плату;
6. проверить имя `Test-DPLS-XXXX`;
7. подключиться по фирменному 128-bit Service UUID;
8. прочитать `DEVICE_INFO_REPORT` и убедиться, что полный `device_id == serial_number`;
9. выполнить BLE pairing/auth smoke test;
10. сохранить результат в производственную БД.

Factory HEX можно записывать тем же программатором PHY62x2, которым прошивается обычный Intel HEX. Он содержит отдельную секцию с адресом `0x1103F000`.

Пример для текущего стенда:

```sh
tools/flash_firmware.sh tmp/test-dpls.hex
tools/flash_firmware.sh tmp/factory-00012874.hex
```

Не использовать `--erase` между этими шагами.

## 8. Производственная БД

Минимальная запись на единицу продукции:

```text
serial_number
hardware_revision
chip_factory_mac
ble_address_source       # chip_public / static_random
ble_address              # фактически проверенный адрес
factory_record_sha256
firmware_version_at_test
production_timestamp
test_station
test_result
```

IRK/CSRK не следует писать в обычные логи или CSV оператора. Если компании требуется резервное хранение секретов, оно должно быть отдельным защищённым хранилищем с контролем доступа.

Уникальность `serial_number` должна обеспечивать производственная система до выдачи factory HEX. Firmware не пытается самостоятельно «занять следующий номер».

## 9. Factory reset и обновление firmware

Обычный factory reset устройства может очистить:

- пароль/верификатор;
- пользовательское имя;
- bonds;
- runtime lock state;
- прочие пользовательские настройки.

Он **не должен** менять:

- `serial_number`;
- BLE address;
- factory IRK/CSRK;
- hardware revision из factory record.

Обычное обновление firmware также не затрагивает `0x1103F000`.

Полный chip erase — сервисная/производственная операция. После него прибор нельзя выпускать или возвращать заказчику, пока factory identity не восстановлена из производственной записи и не пройдена повторная проверка.

## 10. Advertising и Bluetooth Company Identifier

Новая прошивка не отправляет Manufacturer Specific Data с `0x0B01`.

В эфире остаются:

- стандартные BLE flags;
- фирменный 128-bit Service UUID `7b5f1000-5d7a-4d2f-9a4c-14b7d5f00001`;
- имя `Test-DPLS-XXXX` в scan response.

Это соответствует архитектуре ТЗ: приложение обнаруживает Test-DPLS по фирменному Service UUID, а серийный номер/состояние получает через имя и GATT.

Мобильный код пока может распознавать старый manufacturer payload для обратной совместимости с ранними прототипами, но новая серийная прошивка его больше не создаёт.

## 11. Критерии готовности к серии

Перед первым серийным выпуском проверить на реальном стенде:

- минимум 10 плат получают разные `serial_number`;
- `device_id` не меняется после reboot;
- `device_id` не меняется после обычной перепрошивки;
- BLE address не меняется после reboot/перепрошивки;
- factory reset не меняет serial/address/IRK;
- удаление SNV не меняет identity у провиженного прибора;
- полный erase действительно блокируется сервисным скриптом без override;
- после намеренного chip erase и повторного provisioning прибор возвращает тот же serial;
- две платы с одинаковым serial не могут пройти производственный acceptance;
- приложение фильтрует приборы по Service UUID и корректно показывает `Test-DPLS-XXXX`.

После этого источником истины по идентичности считается производственная БД + factory record, а MAC больше не используется как бизнес-идентификатор прибора.
